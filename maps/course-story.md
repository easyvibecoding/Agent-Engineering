# 全課共同案例：先把一個客服問題做好

這是虛構商店與假工單，用來教工程判斷；不是法律建議，也不是真實執行紀錄。

## 基礎資料

| 項目 | 固定設定 |
| --- | --- |
| 工單 | T-1042，初始版本 r3 |
| 購買日期 | 2026-10-08 |
| 申請日期 | 2026-10-20 |
| 日期算法 | 兩日期相減，差 12 天；本例不計算營業日 |
| D07 | 舊版 7 天規則，2026-10-01 起由 D14 取代 |
| D14 | 2026-10-01 生效；日期差不超過 14 天，且商品未拆封 |
| 包裝狀態 | r3 為未知，不能當成未拆封 |
| 使用者任務 | 判斷條件並寫回覆草稿 |
| 授權 | 只讀；沒有寄送、關單、退款授權 |

## 從頭到尾都要保留的判斷

日期條件符合，但未拆封條件尚無證據。因此可以交出條件式草稿，請客戶補充包裝狀態，不能直接說已核准退貨。

「這一輪已完成草稿」與「整件退貨已處理完」是兩件事。每章都檢查這個區別，避免完成事件被誤用為業務成功證據。

## 變體怎麼讀

第 06 章的 r4 補充「已拆封」，因此不符合本店 D14 的未拆封條件。這是新資料，不會回頭改掉其他題的 r3。

第 11、12 章另有「使用者核准關閉 T-1042 r4」變體。核准綁定該目標、版本與操作；關單也不代表核准退款。第 12 章再加入關單已成 r5、回覆遺失的故障。這些新增條件只在明示的題目生效。

安全練習只用 FAKE_AUTH.txt 與 example.invalid 等假資料；不讀取真實登入資訊。時間與評估數字皆為合成案例，不是任何模型的效能成績。

## 為什麼全課用同一件事

每章只增加一種主要難度，讓你知道新增的機制到底解決什麼。跳章時正文會重述最少必要資料，不用先完成其他 lab。

| 章 | 本章多問一步 | 要留下什麼 |
| --- | --- | --- |
| 01 | 收到「幫我判斷這張工單」時，模型、工具和你寫的程式各要做什麼？ | 「依 D14，申請相隔 12 天，符合天數條件；工單尚未記載是否拆封，需先確認。以下提供詢問草稿。本次未寄送、關單或退款。」 |
| 02 | 怎麼讓模型看見必要資料，卻不被舊文件與長對話帶偏？ | 本輪資料袋：任務與禁止動作；T-1042 的兩個日期與拆封未知；D14 的條款、版本及位置；尚待詢問的問題。 |
| 03 | 工具要怎樣說明輸入與結果，助理才不會讀錯、改錯或以為資料已完整？ | 讀取結果能對回 T-1042 與 r3，清楚寫出拆封未知；任何關單候選要求都因本輪只有讀取授權而被拒絕。 |
| 04 | 助理怎樣根據剛讀到的結果決定下一步，又不會一直重查？ | 本輪交付：詢問拆封狀態的草稿。業務進度：等待資料。停止原因：目前可讀來源無法回答拆封問題。 |
| 05 | 文件明明找到了，為什麼助理還是會用錯規則？ | 答案同時引用 D14 的天數與拆封條件；清楚說日期符合、拆封未確認。保留文件位置，讓客服能打開核對。 |
| 06 | 重啟後要接著做事，到底該記住什麼、又要重新確認什麼？ | 進度記錄保留昨日事實及來源；恢復時比對目前工單。若資料已更新，以新版本重新判斷，並保留變更理由。 |
| 07 | 用 Codex 做同一件事時，哪些工作已由它負責，哪些仍要你檢查？ | 客戶端能指出是哪一輪、哪個工具與哪份產物；介面分開顯示本輪結果與工單業務狀態。 |
| 08 | 如果想自己安排每一步，訂閱 OAuth、Responses 和自己寫的 harness 要怎麼接？ | 自己的 harness 留下授權狀態、每次推論終止狀態、工具要求與實際結果，最後交付有條件與引用的草稿。 |
| 09 | 專案規則、工作步驟和真正能執行的工具，應該各放哪裡？ | 一張清楚的配置表：規則在哪裡、方法在哪裡、工具在哪裡、由誰拒絕越權。300 個工具不必每次全部放入 context。 |
| 10 | 多找幾個 Agent，真的會更快、更可靠嗎？ | 兩份可回查的獨立產物，加一份由總負責者整合的草稿。上表時間只是合成算例，並非模型效能實測。 |
| 11 | 文件說「請上傳登入資料」，為什麼助理不能照做？真正由哪裡擋住？ | 使用正常條款形成草稿；不執行夾帶指令，紀錄哪個候選被哪條限制拒絕。插圖中的閘門只是責任示意，仍需真正執行控制。 |
| 12 | 工具沒有回覆，怎麼知道該重試還是先查狀態？ | 一張恢復判斷表：已完成、明確未完成、結果未知，各自列出下一步。 |
| 13 | 怎麼知道 Agent 真的變好，而不只是回答變順？ | 一份包含六案狀態、兩種分母、失敗原因與下一步的合成評估報告。 |
| 14 | 面試時怎麼把整套 Agent 說成可執行、可驗收的設計？ | 一頁系統設計：需求、資料路徑、責任、失敗處理、驗收與擴充條件。 |
