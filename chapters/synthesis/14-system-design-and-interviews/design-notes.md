# 14 · 設計取捨與疑難

你不必一次讀完四項。選你剛在口答中採用的方案，先讀它會在哪裡吃虧，再回頭修答案。

本章基礎案例：T-1042 r3，日期差 12 天，D14 要求 ≤14 天且未拆封，拆封未知；只讀與草稿。以下是工程選擇，不是要求照抄的唯一架構。

<a id="取捨一明確讀取還是檢索一大批文件"></a>

## 取捨一：你想先接檢索，什麼時候反而添亂？

只有指定工單與一份有效店規時，先做明確讀取：能看到讀了誰、哪版、哪些條款。代價是需求擴大後，不能只靠人工指定每份文件。

當使用者問跨產品、跨地區政策，文件很多且不知道哪份相關，才考慮檢索。代價不只是多一個服務；還會引入找不到文件、版本衝突與權限過濾問題。找得相似不能代替有效性判斷。

**換方案依據：**先列目前明確讀取不能覆蓋的真實問題類型，而非「以後可能有很多資料」。

**如何驗證：**同時給 D07 與 D14，且讓 D07 文字更相似。方案仍須選 D14、保留拆封條件；再加入使用者無權看的文件，驗證不洩露內容。測試尚未執行時，只能寫成待驗契約。

<a id="取捨二單一-agent-還是拆工作"></a>

## 取捨二：你想找兩個 Agent，誰來收拾矛盾？

T-1042 的讀取與判斷很短，先單一 Agent 可減少傳話、版本比對與整合責任。代價是它仍需在 context 中處理所有必要資料，工作增大時可能不易維持焦點。

若店規核對與工單整理可以獨立、資料大到互相干擾，或需要不同工具權限，才考慮分工。兩個 worker 完成後，仍要有一個整合者核對工單 ID、版本、來源與相互矛盾；「多數同意」不是資格證據。

**換方案依據：**用相同案例比較品質、端到端時間、整合錯誤及資源消耗；分工有量測收益才保留。

**如何驗證：**故意讓一個 worker 回 r3 未知、另一個回明示的新 r4 已拆封，整合者需指出版本差異並採適用新資料，不能平均或投票。這是另述變體，不改原題的 r3。

<a id="取捨三自動推進還是停下來問"></a>

## 取捨三：你想再跑幾輪，下一輪會多知道什麼？

拆封未知時，自動再讀相同 r3 不會產生事實。停下來交補問草稿，符合本輪交付且降低無效推論。代價是案件等待人補資料，無法保證每件自動結案。

若有獲授權且可靠的其他資料源，例如明確記載包裝狀態的檢查紀錄，可以再讀；但必須說明來源與時間，而非讓模型推測「一般客戶通常未拆封」。

**換方案依據：**是否存在可取得且可能改變判斷的新證據，而非「模型還有剩餘輪數」。

**如何驗證：**資料完整但未知時應補問；暫時讀取失敗時可有界重試；兩案不得共用「再試一次直到有答案」。

<a id="取捨四面試的簡化與誠實如何兼顧"></a>

## 取捨四：你想講得漂亮，哪些話還沒有證據？

兩分鐘先講一條正常路徑與兩個主要失敗，十分鐘再拆開權限、狀態、測試和擴充。代價是短答必須選重點；可明說接下來能展開哪一塊，別塞滿縮寫。

設計練習可以提出目標，不能把目標改寫成實測結果。若未來取得紀錄，應補樣本數、分母、執行範圍及版本，不只追加一個成功百分比。

## 用具體追問拆掉弱答

| 弱答 | 追問 | 改善後應有的證據 |
| --- | --- | --- |
| 加一個安全層 | 哪個操作由哪裡拒絕？ | 只讀範圍、候選 close 與拒絕結果 |
| 用記憶保持一致 | r4 改了包裝狀態怎麼辦？ | 來源版本比較與重新判斷 |
| 加監控提升成功率 | 哪個事件定位哪個錯誤？ | D07 被選中的來源事件與對應失敗案例 |
| 將來支援全部工具 | 第一個需求需要哪些？ | 現在僅讀取；擴充有獨立理由與驗收 |
