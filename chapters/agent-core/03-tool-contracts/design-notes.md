# 03 · 設計取捨與疑難

你把工具拆開後，可能馬上遇到另一個問題：工具變多，助理反而挑得更慢。這不是前面白做，而是開始碰到設計的代價。

一次只選一項讀。先寫「我會選哪個」，再往下看何時吃虧。以下仍是 T-1042 r3 的合成只讀案例，拆封未知；設計選擇不是 API 強制格式。

## 取捨 1：一個 execute，還是按業務操作拆工具？

你可能想先留一個 execute，因為前端只要接一次。當它同時接受讀取、關單與退款，這份方便就會變成授權難以看懂。三者後果不同，因此本例先拆成 read_ticket、close_ticket、refund，讓操作名稱能直接對應權限、紀錄和驗收。只讀任務可以僅提供讀取工具；後端仍依真實呼叫者拒絕寫入。

代價是工具說明變多、模型選擇負擔增加，也可能產生額外往返。例如讀基本資料與讀包裝狀態若總是同時使用、同來源同權限，可以合併成一次 read_ticket。不能只為「原子化」而讓每個欄位各查一次。

若已經有共用 execute，未必需要立刻全面重寫；可在外面提供有限的具名入口，或將 action 限成明確列舉並由後端逐項授權。關鍵是權限邊界可驗證，不是函式名稱數量。

**如何驗證：**用合法讀取、未授權關單、未知 action 三種要求核對：讀取成功；另外兩種在外部狀態改變前被拒。檢查紀錄是否能指出哪個操作被拒，而非只留下 success=false。

## 取捨 2：回整份工單，還是任務需要的欄位？

你可能想把整份工單回去，避免以後再查。代價是每個任務都要看不必要的資料，甚至收到不該需要的個資。本例先回 ID、版本、日期、包裝狀態與來源。好處是模型少處理無關欄位，也避免暴露任務不需要的敏感內容；代價是新任務可能需要再讀別的欄位。

只有當多數任務都需要同一組資料、一次取得的成本可接受且身分有權讀取，才考慮擴大預設結果。不要為了減少一次往返，把所有客戶資料放進每個模型請求。

**如何驗證：**以 D14 每個條件對照回傳欄位：日期有證據、拆封保留未知、來源版本可回查；額外個資不因「方便」出現。若缺必要欄位，介面應說明未提供並允許正當續取，不得默認為符合。

## 取捨 3：用布林、null，還是列舉表示拆封狀態？

你可能選布林，因為 opened=true／false 很短；但讀者容易將 false 誤看成「沒填」，也可能因預設值遺失未知。本教材選 opened／unopened／unknown 三值列舉，名稱較長卻能直接表達來源觀測。

既有資料若採 opened=null 表未知，也可保留；代價是每一層都必須維持 null 的意義，不能在轉換時用 false 補掉。列舉也不保證來源真實，來源沒查證仍然可能填錯。

**如何驗證：**分別給已拆、未拆、未填三份合成輸入，核對工具與草稿是否維持三種不同結論。只驗證 JSON 能解析不足以發現錯誤。

## 取捨 4：一次完整回傳，還是分頁／摘要？

你可能想一次全部回完，省去續頁；資料小且固定時，這確實很合理。結果大或長度不穩定時，分頁能控制單次傳輸和 context；代價是續取、重複項目、途中失敗與資料變動都要定義。

摘要適合概覽，不能自動取代精確統計。若工具只回「很多案件」，就不能支援「全部有幾件」的驗收。若任務只尋找某個 ID，找到即可停止，不必為了使用分頁而掃完整庫。

**如何驗證：**先安排同一固定查詢快照，第一頁 10 個不同 ID、第二頁 4 個不同 ID 且兩頁不重複，最後頁明確結束，才可報該快照查詢內完整 14 個唯一項目。再安排第二頁失敗、1 筆跨頁重複、翻頁期間資料變動或 cursor 不前進；助理應分別標部分結果、去重後 13 個 ID、無單一時間點完整性保證、工具異常，不能只用 10+4 一律判為完整 14。

## 疑難對照

| 弱答 | 缺了什麼 | 改成可驗證的說法 |
| --- | --- | --- |
| 「工具安全就好」 | 沒有執行責任與拒絕條件 | 「服務根據可信身分拒絕未授權 close_ticket，狀態保持未變」 |
| 「has_more 我會看」 | 沒說任務是否需要完整資料 | 「若要全量統計就續取；若只找已取得的 T-1042 就停止」 |
| 「出錯 retry 三次」 | 沒區分錯參數、無權限與可能已寫入 | 「暫時讀取有限重試；未知寫入先查操作結果」 |

只修一項就好：我原本選 ______，在 ______ 情況會吃虧；我用 ______ 觀測驗證。
