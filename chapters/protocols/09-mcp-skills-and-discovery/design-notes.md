# 09 · 設計取捨與疑難

以下採 T-1042 r3 的只讀與草稿任務；細節見[正文](lesson.md)。表格是設計比較，沒有聲稱實際測量。

## 取捨 1：普通函式，還是 MCP？

只有一個應用、兩個穩定讀取函式時，直接整合容易追蹤呼叫與錯誤。若客服桌面與命令列助理都要共用店規服務，才有理由考慮 MCP，把能力介面共用。

| 比較 | 直接整合 | MCP |
| --- | --- | --- |
| 改一個參數 | 同一份程式內修改、檢查呼叫點 | 需考慮不同 client 與契約版本 |
| 多應用共用 | 可能各維護轉接器 | 可共用協定與能力描述，仍需各 host 整合 |
| 故障定位 | 函式失敗與資料錯誤 | 多出通訊、server 不可用、版本不相容 |
| 權限 | 函式與資料層必須檢查 | Host 與 server 仍須檢查，協定不能代做 |

**代價與換方案條件：**為了兩個函式先架通用服務，可能增加維護工作；反過來，三個應用各自修同一份轉接邏輯，也會浪費。判斷依重複整合與變更成本，不依工具數量口號。

**怎樣驗證：**拿同一份 T-1042、D14 與「無權限」測例，對照結果欄位、拒絕行為與錯誤定位；不要只比能否連線。若要比較耗時，另標實測環境、樣本與分母。

## 取捨 2：專案指引，還是 Skill？

「教材先讓讀者自答」是這個 repo 持續成立的約定，放 AGENTS.md 易於理解。「先查生效版本、再檢查條件」可跨客服任務重用，適合 Skill。

**代價：**方法包按需載入可以縮小 context，但觸發說明不清楚可能導致根本沒載入；把所有流程放 AGENTS.md 則會讓無關任務每次都讀長指引。不要把同一份方法複製兩處，日後改一處漏一處。

**何時換方案：**只有一次性短任務，直接在任務說明寫步驟即可。多個任務重用、需要範例或參考資料，再整理 Skill；只適用特定資料夾的持續規則留在對應作用範圍。

**怎樣驗證：**準備「退貨判斷」「整理一般會議筆記」兩個任務。前者能找到正確方法，後者不被客服流程干擾；拿掉 read_ticket 時，方法須回報能力缺口，而不是編造讀取成功。

## 取捨 3：一次給完整選單，還是分階段探索？

6 個工具可一次讀完整契約；300 個工具若多數無關，可先用領域索引縮小，再讀參數。新增的一關必須有用，不能只因為「按需載入」聽起來進階。

| 風險 | 具體表現 | 改善與驗收 |
| --- | --- | --- |
| 漏掉必要能力 | read_policy 分錯類，助理只讀 D07 舊摘要 | 加入跨類別測例；找不到時擴大一次可控搜尋並保留缺口 |
| 舊契約快取 | 工具要求 ticket_id，host 仍送 id | 工具版本改變時更新；執行前驗證實際契約 |
| 同名誤選 | 測試店與正式店都叫 read_policy | 保留 server 身分與適用範圍，對回來源 |
| 誤把選中當獲准 | 找到 close_ticket 就呼叫 | 執行控制仍以本輪只讀範圍拒絕 |

**何時換方案：**若大量時間花在探索卻沒有減少誤選，可改固定領域路由或人工選定工具。若探索很省 context 卻漏掉關鍵工具，不能只靠「token 下降」宣布改善。

## 卡點：兩個成功不能互相替代

- 列舉成功只表示收到描述；呼叫成功才表示這次動作有結果。
- 通訊成功不表示結果屬於 T-1042；仍核對 id、revision 和政策生效日。
- 有有效資料不表示有寫入授權；草稿產物不能變成已退款。

用 [Q03](exercises/README.md#c09-q03) 找出第一個錯誤推論，再用 [Q04](exercises/README.md#c09-q04) 設計可觀察的防線。
