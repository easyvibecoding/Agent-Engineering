# 09 · 設計取捨與疑難

你可能想一次把所有工具、規則和方法都接好。先拿 T-1042 的只讀草稿任務問：哪一步真的需要增加一層？以下是設計比較，不是效能實測。

## 取捨 1：普通函式，還是 MCP？

**你可能會選 MCP，因為想避免以後重寫。**但現在只有一個應用、兩個穩定讀取函式，先加通用服務也多了版本、通訊和服務啟停問題。

這時直接整合容易追蹤。等客服桌面與命令列助理都要共用店規，且已重複維護轉接邏輯，再評估 MCP 的收益。

怎麼驗證？讓兩種方案處理同一份 T-1042、D14 和無權限測例。看結果欄位、拒絕及故障定位，不只看「連上了」。若比較延遲，另記環境、樣本及分母。

反過來，若三個應用每次政策介面改版都各修一份，繼續直接整合也會吃虧。換方案的條件是重複維護已成成本，不是工具數到某個神奇門檻。

## 取捨 2：專案指引，還是 Skill？

**你可能會把整套方法塞進 AGENTS.md，因為每次都讀得到。**短期簡單，但整理會議筆記也載入長篇退貨流程，無關任務會受干擾。

「教材先讓讀者自答」是持續約定，留 AGENTS.md。「查版本、算日期、問拆封」可重用，才值得封裝 Skill。一次性短任務放當次任務說明也合理。

Skill 的代價是可能沒被找到。描述若只寫「處理資料」，助理未必知道它適用退貨判斷。也不要兩邊複製同一套長方法，否則改一處漏一處。

怎麼驗證？用「退貨判斷」及「一般會議筆記」兩種任務，分別檢查該載入時有載入、不相干時不干擾。拿掉 read_ticket，方法應回報能力缺口，不能補出假結果。

## 取捨 3：一次給完整選單，還是分階段探索？

**你可能會選分階段，因為 300 個工具看起來太多。**它能少讀無關契約，但多一關就可能漏掉必要能力。

先測正常退貨任務能否找工單與有效店規。再故意把 read_policy 分錯類：若系統直接拿 D07 舊摘要頂替，省下的 context 沒有價值。

修正可以是一次受控擴大搜尋；仍找不到就回報缺口。只有 6 個穩定工具時，直接列完整契約可能更簡單；若探索本身拖慢又沒減少誤選，可以改固定分類或人工選領域。

### 深挖時再查這些風險

| 看到什麼 | 修哪裡 | 怎樣驗證 |
| --- | --- | --- |
| 同名工具連錯店 | 來源辨識 | 對回 server、商店及政策版本 |
| id 已改名 ticket_id | 契約快取 | 版本改變時重取，舊參數被拒絕 |
| 列舉後案件權限撤回 | 執行時授權 | 實際呼叫仍拒絕，快取不放行 |
| 搜尋完仍缺店規工具 | 缺漏處理 | 有界補找後停止，不假裝政策已驗證 |

## 卡點：兩個成功不能互相替代

通訊成功可以帶回「無權限」；因此不能寫工單讀取成功。讀取成功也可能回錯案；因此還要核對 id、revision。資料正確仍不等於可以關單；本輪只有草稿授權。

先用 [Q03](exercises/README.md#c09-q03) 找一個推理缺口，再用 [Q04](exercises/README.md#c09-q04) 說明你會怎麼驗證修正。一次修一個責任，不必把所有架構同時換掉。
