# 12 · 設計取捨與疑難

你可能很想直接重送：少查一次，使用者也少等一會兒。這個選擇何時合理，何時會多做一遍？從下面第一個取捨開始；需要存檔設計再讀第二個。以下都是 T-1042 r4 另行核准關單的合成變體。

## 取捨 1：超時後查詢，還是直接重送？

你若不知道第一次有沒有生效，或通知寄出後收不回來，先查詢會多花一點時間，卻避免拿第二次寫入當探針。它多一次查詢與等待，但能避免用第二次寫入調查第一次是否成功。close-T1042-01 在本例已完成，查證後補記就足夠。

你也可能選同 ID 重送來取回結果。這只有在遠端契約涵蓋相同內容、併發、結果重播與有效期間時才站得住腳。它能減少客戶端分支，但服務端需要保存狀態、處理競爭，且不能把不同內容誤合併成同一操作。

**何時換方案：**無查詢介面但有可靠去重契約時，可重送原 ID 取得結果；兩者都沒有時，保留未知交人工比創造新 ID 更合理。去重期限已過，不可沿用先前的安全假設。

**如何驗證：**同一 ID、同一內容的兩次傳送只產生一次關單效果；同一 ID 改內容應明確拒絕或依契約處理，而非悄悄執行；併發兩次也不能各自成功新增效果。驗收同時看工單、操作紀錄與附帶通知，不能只看 closed。

## 取捨 2：檢查點記多細？

你可能已經有聊天紀錄，覺得不用另外存進度。但一句「下一步關單」不會告訴你這是哪次操作，也不能證明上一輪沒做過。

比較能恢復的做法，是在送出前留下原意圖，確認後留下證據。這兩筆紀錄各有用途，不用靠模型從長對話重新猜。

本例最小紀錄：目標 T-1042、原 expected_version r4、核准及指定內容、close-T1042-01、a1、最後已知狀態與證據來源。完成後加結果 r5。不能只存「下一步：關單」，因為不知道哪次關單已做過。

**代價：**寫入頻率、敏感資料保留與格式演進都要管理。每個 token 存檔通常增加成本，卻未增加副作用恢復能力。檢查點也可能落後於遠端，不能把它當唯一真相。

**何時換方案：**純讀取可重算的工作可用較粗粒度進度；一個步驟產生外部效果時，至少把意圖與確認證據分開保存。資料格式更新後仍要能辨識舊紀錄，不能誤認成未執行。

**如何驗證：**在三個中斷點重啟，確認不用完整聊天紀錄也能找到原意圖；刪掉尚未持久保存的記憶體資料後，恢復決策仍成立；紀錄毀損時停止寫入而非猜測。

## 取捨 3：自動收斂，還是保留未知？

每次查詢都失敗時，自動重查能處理短暫網路問題，但無限重查會佔住資源並讓使用者誤以為工作持續進展。本章示例最多查詢 3 次（含首次）、a1 之外最多重送 1 次（a2），恢復流程總時限 30 秒；每次動作前扣對應次數，重送也需保留後續查詢額度，持久紀錄避免重啟歸零。這只是教學預算，服務需依業務等待容忍度調整。

到達上限後，依最後證據標明「已確認未完成」或「結果仍未知」，再附最後證據、已做調查與下一位負責人。人工交接不是把未知改名成成功，也不能把操作 ID 丟掉，否則人工可能再做一次。

驗證時另讓每次查詢都回「明確拒絕且無效果」：最多只出現 a2，不得無限重送 a3、a4。讓查詢一直失敗：應按上限停止、沒有新寫入、能給出可接手資料。再測查詢第二次恢復：應立即依證據收斂，不必耗完全部次數。

讀到這裡可以先停：選出自己方案最昂貴的一個保證，寫下它在什麼條件下失效。下次從下面反例回查。

## 常見說法與修正

| 弱說法 | 缺少什麼 | 改善後 |
| --- | --- | --- |
| 超時就 retry | 未區分讀寫與未知效果 | 先查原操作；只有條件成立才同 ID 重送 |
| 已有版本鎖，所以不會重複 | 版本衝突不能證明原操作結果 | 版本保護舊資料；去重辨識同一意圖 |
| 取消成功，遠端就沒做 | 只取消了本地等待 | 停後續派工，另確認在途操作 |
| 補償就是 rollback | 跨系統效果可能無法撤回 | 另授權補償，列出不能撤回的效果 |
| 本地寫 done 就算完成 | 沒有外部效果證據 | 保存與目標相符的原操作結果 |
