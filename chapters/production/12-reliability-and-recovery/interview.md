# C12 · 面試與追問

## 主問題

「你如何避免 Agent 重複執行有副作用的工具？」

先按兩分鐘計時自答，先別看骨架。答完只找一個漏項，重說那一段就好。以下是練習設計，不是真實面試成績；本 repo 的 lab 未實作。

## 短答骨架

1. **先說風險：**a1 已關閉 T-1042 成 r5，但回覆遺失，超時不能直接判定未執行。
2. **再說操作身分：**持久保存 close-T1042-01 與核准、r4、原內容；傳送另有 attempt_id。去重保證需要服務端配合。
3. **說恢復：**先查原操作與目標，相符便補記完成；明確無效果才檢查重試前提；未知則有限查證後交人工。
4. **說限制與驗收：**版本與去重分責，取消不撤銷已有效果；故障注入觀察效果與附帶事件，跨系統不空口承諾 exactly once。

骨架用來檢查漏項，不要逐字背。能指出資料、決策與證據，比堆出所有機制名稱更重要。

## 面試官可以依序追問

一次只問一列，讓學習者答完再選下一題。不需要把整張表當成一題。

| 追問 | 要檢查的能力 |
| --- | --- |
| 只讀到 closed r5，能說是你完成嗎？ | 現況與操作歸因分開 |
| a2 的哪些欄位能變，哪些不能？ | 同一意圖與新意圖的界線 |
| 去重保存 24 小時，兩天後重啟怎麼辦？ | 保證期限，不能盲目重送 |
| a1 還在途，這時使用者按取消？ | 停止新工作，確認已發效果 |
| 關單後寄信也超時，你的 transaction 管得到嗎？ | 跨系統範圍與觀察限制 |
| 你怎麼證明不是只有畫面看起來正常？ | 操作歷程、版本、附帶效果驗收 |

24 小時是追問的假設條件，不是任何產品的固定去重期限。

## 常見弱答如何改善

「我會 retry 三次」→ 先問讀或寫、效果是否未知，再交代為何可重送。

「我用 UUID 所以不重複」→ 交代服務端如何比對原要求、併發與有效期；光有 ID 沒有保證。

「出錯 rollback」→ 列出能回復的資料與已寄通知等不可撤回效果，補償另需授權。

「最後是 closed 就通過」→ 同時檢查操作歸因與通知／歷程是否重複；未知情境如實停止也可能是正確行為。
