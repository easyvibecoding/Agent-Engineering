# 11 · 設計取捨與疑難

你可能已想出一個最直覺的方案：任何工具都先問人。它確實把決定留給人，但一天跳出幾十次確認後，人還會逐一看清楚嗎？下面沿著三個常見選擇，看看何時會吃虧。這些是本例設計推導，沒有部署證據。

## 取捨 1：預先限定範圍，還是每個動作都詢問？

你若選「先把可讀範圍列清楚」，本例就很適合：原任務只讀 T-1042 r3 和 D14。允許這兩份資料、拒絕其他資源，比每次詢問更容易理解與驗收。

這個選擇會在範圍改變時吃虧。清單過窄可能漏掉真的必要資料，導致任務停在缺資料。若只寫「客服資料皆可讀」，又會把其他案件暴露給助理。範圍應至少含資源 ID 與允許動作；必要時還要限定租戶、版本或欄位。

若使用者新增「把草稿寄給客戶」，寄送是新副作用。先準備收件人、內容與影響，依現有授權判斷能否執行；缺授權才請核准。文件自己說必須上傳，不能作為擴權理由。

先用一個允許案例確認它可用：允許讀 T-1042 的正向案例應成功；讀 T-1043 和 FAKE_AUTH.txt 的反向案例應在讀取前拒絕。若全數拒絕，雖未洩漏，仍沒證明可完成任務。核准文字若含糊，不應由模型自行補出範圍。

## 取捨 2：依靠內容偵測，還是限制可做的動作？

你也可能想「把攻擊句先刪掉」。內容偵測可提示可疑段落，幫助模型避免產生越權候選。但對外部資料無法保證全部辨識，重要限制仍要放在實際讀寫入口。

不過兩種做法各有成本。執行限制需要清點工具與資源，通用 shell 或可任意查詢的伺服器特別難收斂。只限制一個入口，另一個仍可繞過。內容偵測則可能把正常政策引用誤判成攻擊。

如果只需讀兩份固定假資料，直接提供這兩份內容即可，沒有必要提供任意檔案工具。若工作確實需要廣泛搜尋，再增加受限查詢工具，而非一次開整個檔案系統。

要知道自己守住哪一層，分開測模型是否提議越權，以及執行器是否拒絕越權。即使模型每次都說拒絕，也要直接提交假禁止候選驗證執行層。反過來，模型提出攻擊候選但執行器成功拒絕，代表攔截有效，模型辨識仍需改善，兩項成績不能混在一起。

## 取捨 3：核准後要不要重新確認版本？

你可能覺得「剛才才核准，不用再查」。但使用者核准 close T-1042 r4，代表看過的是 r4 情境。真正寫入前比對 ID、版本與具體內容，能防止錯案件和過時決策。

嚴格版本比對也有代價。版本只增加了一個無關標籤，也可能觸發停止。若一律每次重新問人，會增加等待；若一律忽略版本，又可能漏掉客戶新訊息。

簡單系統先用嚴格預期版本，任何差異停止核對；成熟系統可明確定義哪些變更影響核准，但這需要業務規則與可觀察測試，不能讓模型自行猜測「應該沒關係」。

先用四個小變化看出邊界。準備四個候選：正確 T-1042 r4；錯 ID；錯版本；內容偷偷增加寄信。只有第一個符合核准。測試再加入核准檢查後、寫入前版本改變的案例，確認寫入端本身檢查前置條件，避免先查再寫之間出現空窗。

## 常見說法怎麼改

如果你的設計只剩一個口號，從下面挑一列補成可觀測的句子。一次修一列就好。

| 弱說法 | 缺少什麼 | 可驗收的改寫 |
| --- | --- | --- |
| 我們採最小權限 | 沒列實際資源與能力 | 本輪只能讀指定 T-1042 和 D14，無任意路徑及業務寫入。 |
| 我們有 sandbox | 名稱未描述範圍 | 另列程序可讀、可寫、可連線範圍，以及各自的正反向測試。 |
| 有人按核准就可以 | 沒綁目標、版本、內容 | 比對 close、T-1042、r4、已審查影響；任一不符拒絕。 |
| 回答說沒傳，所以沒事 | 未觀測工具與程序 | 同候選無傳輸事件；正式程序網路是否受限另外查證。 |

## 疑難：拒絕了外傳，但檔案先被讀了，算通過嗎？

不算完整通過。本例同時禁止讀假敏感檔與外傳；外傳未發生只能通過其中一項。應記錄讀取控制失敗、傳輸控制成功，並檢查假內容是否已進模型 context 或 log。不能把部分攔截寫成全部安全。
