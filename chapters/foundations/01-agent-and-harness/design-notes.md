# 01 · 設計取捨與疑難

你已經知道 T-1042 缺包裝資訊，接著要決定怎麼寫系統。這時最容易多做一步：為了「這是 Agent 課」，把每個判斷都交給模型。

以下三個選擇各看一個就好。仍用合成 r3、12 天、D14 且包裝未知，只准草稿；沒有新增寫入授權。

## 取捨一：固定流程、模型分類，還是模型選下一步？

你可能先選 Agent，因為客服問題看起來很多變。先把問題縮小：如果只有日期與包裝兩個固定欄位，缺資料就套固定詢問，需要臨場選路的地方在哪裡？

如果找不到，先用 workflow。代價是每個合法分支都要明確寫出來，但它容易重現、容易定位錯誤。

接著看一個小變化：包裝資訊變成自由文字「盒子打開過」。這時可以加模型抽取欄位，保留原句與未知，外面仍用固定流程。你多承擔了抽取錯誤，不代表已需要自由選工具。

再往前一步，附件種類與來源真的不固定，下一個來源得讀完上一份才知道，才評估有限 Agent。代價會變成路徑難重現、容易重複查找，需要保留每次選擇與停止原因。

**何時換方案？** 用同一批完整、缺漏與舊版來源案例比較。固定流程若經常無法理解新來源而交人工，模型選路又能找回有效證據，才有具體理由加複雜度。反過來，若實際路徑大都固定，就可以退回簡單方案。這是待驗證的設計條件，不是教材已量出的結果。

## 取捨二：讓模型自我約束，還是由控制程式攔截？

你可能已在 prompt 寫三遍「不准關單」，於是以為夠了。若未來有關單工具，而它直接接受模型參數，一次偏離就可能改變工單。

本例先只給必要的讀取能力，再讓執行端拒絕越權候選。這要多維護工具與授權規則；規則太窄也會誤擋合法讀取。連 T-1042 都讀不到時，系統應說無法取得資料，不能用一個漂亮草稿掩蓋缺漏。

你可以用三個候選審閱設計：讀 T-1042 應通過；讀無權目標應拒絕；關 T-1042 應拒絕。驗證時看實際工具路徑與事件，因為「先說拒絕、之後照樣呼叫」仍是控制失效。

未來若真的要寫入，另設核准範圍、精確目標與狀態讀回。不是拿掉今天的限制就完成新設計；本章也沒有那份授權。

## 取捨三：只有「成功／失敗」，還是分開記錄兩層完成？

你可能只想放一個綠色「完成」。如果客服看完就以為退貨辦好了，這個簡單介面反而增加接手錯誤。

T-1042 同時有兩個合理狀態：本輪草稿完成，資格仍等待包裝資訊。把兩者分開，呼叫端才知道收到什麼、下一步等誰。

代價是介面要解釋狀態關係，欄位也會增加。若工作只是改一個本地欄名，單一完成狀態可能已足夠，不必處處放兩層。

**怎麼驗證？** 給審閱者看狀態與產物，請他說下一步。他若說「已退款」，就回去修文字或呈現。這是要做的理解檢查，並非已取得真人或模型評測成績。
