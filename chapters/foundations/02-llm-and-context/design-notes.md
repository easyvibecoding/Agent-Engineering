# 02 · 設計取捨與疑難

本章共同前提：T-1042 r3，差 12 天；現行 D14 要求 ≤14 天且未拆封；拆封未知，只准判斷與草稿。以下是教材設計選擇，不是某個 API 的要求。

## 取捨一：必要資料預載，其餘按需讀

**採用時機。** D14 很短，而且每次判斷都用得到，預載完整兩條件可少一次往返。30 頁歷史並非本輪必需，先留可回查索引，不把全文當保險。

**代價。** 按需讀需要額外工具往返，模型也可能漏判何時需要補讀；預載則增加輸入量，若沒更新還會每輪重複送出舊版。兩者都需要來源與版本管理。

**何時換方案。** 若多數工單都需要同一頁例外條款，應考慮一起預載，而非每輪再查。如果任務改為追查政策演變，就帶 D07 與 D14，清楚標明歷史與現行。不能用「舊文一定無用」當永久規則。

**如何驗證。** 用相同工單與來源，比較是否漏未拆封條件、引用錯版、補讀次數及完整完成時間。所有方案都必須有權讀到相同來源，才是在比較選取策略；不能一組缺原文、一組有原文，再把差異都歸給模型。

## 取捨二：摘要保留決策條件，原文仍可回查

**採用時機。** 對話已有大量重複搜尋，但下一輪只需要接續缺漏詢問，可以用五行交接代替完整歷史。

**代價。** 摘要會失去細節，且撰寫者可能把「日期符合」縮成「整體符合」。把摘要當唯一真相，後面每次壓縮都可能放大錯誤。

**何時換方案。** 若涉及爭議、原始措辭或政策例外，應補讀原文。當任務改為審計過程，摘要只能導航，不能取代事件紀錄。工單更新時也要重新核對來源版本；不能一直沿用 r3。

**如何驗證。** 先列不變條件：ID／版本、日期、適用 D14 及兩條件、拆封未知、只准草稿。逐項比原文與摘要，再讓另一位讀者只憑摘要回答「還缺什麼」。漏任何一項就回修；不以摘要字數更短當通過。

## 取捨三：結構化輸出到什麼程度

最少可用固定欄位區分依據、已知、未知與草稿，方便檢查。過度細分會增加閱讀與維護負擔；欄位數量增加也不等於事實更可靠。

若下游只顯示草稿，簡短結構可能足夠；若程式依 eligibility 做分支，就要明確容許 unknown，避免只用 true／false 強迫二選一。這是業務語義設計，不只是換 schema。

驗收先拿「日期符合但拆封未知」測試：若格式迫使輸出可退／不可退其中之一，先改資料模型。之後才查欄位合法、來源正確、判斷受支持三關；不能把第三關交給 schema。

## 常見弱做法與修正

| 弱做法 | 為什麼失敗 | 修正後要看到什麼 |
| --- | --- | --- |
| 全文載入，交給模型自己選 | 版本衝突仍在 | D14 生效與 D07 被取代資訊清楚可見 |
| unknown 改成 false | false 可能被讀成未拆封 | 專用未知狀態與來源 r3 |
| 摘要只留「符合」 | 丟失另一個必要條件 | 日期符合、拆封待確認分開 |
| 只驗 JSON | 合法字串仍能引用錯版 | 來源與結論逐項比對 |
