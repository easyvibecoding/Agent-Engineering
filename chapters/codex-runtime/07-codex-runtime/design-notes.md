# 07 · 設計取捨與疑難

你可能已經決定「先做漂亮工作台，再接 Codex」。先挑下面最接近你的那個選擇，看看它會在哪裡增加成本；不用一次讀完三項。背景仍是[正文](lesson.md)的合成草稿任務。

## 取捨 1：一份報告，值得先做完整客戶端嗎？

你可能想一次做滿歷史與核准 UI。但若客服今天只需一份草稿，這筆整合成本會先擋住交付。

**先從較少整合開始：**客服自己執行一次、輸入固定、交一份草稿；用 CLI、exec 或合適 SDK 起步。exec 可讓既有腳本收報告，SDK 適合程式管理建立與接續工作。代價是產品互動較少，需要自己決定怎樣呈現錯誤與保留輸出。

**換 app-server 的條件：**真的要將逐步事件、對話歷史及核准互動嵌入自訂畫面。代價是初始化、請求與回覆對應、連線、事件分流、失敗呈現與版本相容。不要因「可能將來會做 UI」就讓第一份草稿依賴這些工作。

**如何驗證：**列三個真實使用動作：送任務、看部分進度、處理失敗。若薄入口已滿足，保留它；若核准必須在自己的工作台精確回覆，就寫出需要的 thread／turn／item 對應，才有升級理由。兩方案都須驗收 D14、12 天與拆封未知。

## 取捨 2：畫面快一點，還是少給錯誤的成功感？

串流讓客服提早看到草稿方向，但字句尚未完整，後面可能失敗。本例「可以退…」若立即觸發綠色成功，會把不完整結論變成業務承諾。

你也可能想讓綠勾越早出現越好。吃虧的時刻是：客服已把片段當承諾，後面執行卻失敗。

**先保留這個區別：**即時顯示片段，清楚標示產生中；本輪 completed 後再進入內容驗收。畫面分兩欄：「本輪：完成草稿」與「工單：等待拆封資料」。代價是狀態比單一轉圈／打勾複雜，但客服能知道還缺什麼。

**何時換呈現：**純批次報告可以只交終止結果；需要除錯再展開工具時間線。這是顯示層簡化，不是丟棄錯誤或把所有 item 成功視為整輪成功。

**如何驗證：**把同一份片段接上 completed、failed、interrupted 三種結尾。三次畫面要有不同終止說明；只有內容通過的 completed 案能標草稿可審閱。三案都不得自動顯示已退款。

## 取捨 3：省掉核准互動，還是保留變更能力？

你可能想把關單工具先接上，「反正之後會用」。但 T-1042 基礎任務根本不需要寫入。最簡單的設計是提供假資料讀取，不接寄送、關單與退款工具；草稿回傳畫面，不必取得檔案寫入權。這能減少誤操作途徑，代價是不能直接替客服完成後續動作。

只有另行取得精確業務授權，才評估新增寫入工具及核准流程。能力、runtime 權限和業務授權需同時成立；核准 UI 必須知道目標與候選操作。不要讓「允許這次讀檔」被解讀為整個對話都能關單。

**如何驗證：**在未來隔離測試環境提出一個未授權寫入候選，應被真正控制點拒絕。還要檢查外部工具的權限，不能用本機 sandbox 宣稱所有 connector 都只讀。現階段只寫驗收契約，不實際操作。

## 常見卡點

| 弱說法 | 補上什麼才可驗收 |
| --- | --- |
| SDK 都是 app-server 的包裝，所以選哪個都一樣 | 指出具體套件與版本；比較需要的互動及由誰掌控循環，不能以單一語言實作概括全部 |
| turn/completed 有 completed，所以成功 | 指出介面與 turn.status，再驗收產物和業務狀態 |
| 設成 read-only，所以只讀指定兩檔 | 分開讀取範圍與寫入限制，查有效權限，不由模式名稱推定所有邊界 |
| 輸出寫沒有關單，所以證明沒關單 | 檢查可用寫入能力、工具紀錄與相關外部狀態；最終文字只是陳述 |
